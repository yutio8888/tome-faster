# 存档体积能否在不增加保存时间的前提下缩小？

后续实验及更严格的全进程 user CPU 门槛见 [0.2.11 验收报告](save-compaction.md)。
下文是 0.2.10 的历史结果，不代表 0.2.11 三项实验已获默认启用资格。

2026-09-14。**紧凑的内部对象编号已实装为 Faster ToME4 0.2.10 的默认功能。**
正式包的完整保存、原版读档器重载和读回后再次保存均已验证。
下文分别保留早期隔离原型的测量，以及正式代码的独立验证，避免混用两个批次。

这里把“不影响时间”理解为同时检查同步 `Game.saveGame` 调用和整个保存流程，
不能只把工作挪到后台或延后重压缩，就称为没有时间成本。

## 正式 0.2.10：20 组保存对照

同一正式 addon 包，仅切换 `compact_save_names`；使用未修改的 ToME 1.7.6、内嵌 LuaJIT 2.0.2、
Linux Xvfb/llvmpipe，原画质和背景保存设置。FBO 保护与 500 ms 受击方向提示限制保持默认开启，
不启用内置 profiler。每次均从同一原始存档复制到新的 home 后正常保存。

首批 5 组的时间波动较大，因此预先固定再跑 15 组交替顺序，并将全部 20 组合并报告，
不剔除较慢样本。下表为各 20 次的中位数；原始单次值和配对差值见
[完整结果](save-names-results.json)。

| 指标 | 关闭短编号 | 开启短编号 | 变化 |
| --- | ---: | ---: | ---: |
| 主档大小 | 2.667 MB | 2.480 MB | **−7.00%** |
| 同步 `Game.saveGame` wall time | 157.76 ms | 159.22 ms | +1.46 ms，+0.93% |
| 同步调用主线程 CPU | 141.42 ms | 142.36 ms | +0.66% |
| 保存完成总 wall time | 510.80 ms | 498.49 ms | **−2.41%** |
| 保存全程主线程 CPU | 416.62 ms | 408.06 ms | −2.05% |

同步调用基本持平，单次 wall time 范围分别为 139.76–173.83 ms 和 144.12–167.22 ms。
短编号发生在后续原有序列化阶段，本批没有观察到总保存时间回退，但不能保证每次调用都更快，
也不能把原型的 5.5% 总耗时下降直接作为正式版收益。不会为缩小目录而附加一次重压缩或迁移。

40 次正式保存均正常结束、无 Lua 错误、保存前后选定状态一致，每个主档均为 2,864 个对象条目。
另完成普通档与短编号档的原版读取器重载，以及短编号档读回后再次保存、再用原版读取器重载。
所有检查的 ZIP CRC 通过；原始存档 ZIP 和保留的 25 个基准文件 SHA256 不变。

## 当前空间用在哪里

只读分析保留的存档副本，25 个文件共 **21.908 MB**；本文 MB 为 1,000,000 bytes。
源文件在分析前后逐一核对 SHA256，无变化。

| 内容 | 体积 | 占目录比例 |
| --- | ---: | ---: |
| 21 个历史区域档 `.teaz` | 18.749 MB | 85.6% |
| 当前主档 `game.teag` | 2.663 MB | 12.2% |
| 保存截图 `cur.png` | 0.433 MB | 2.0% |
| 日志和描述 | 0.064 MB | 0.3% |

`.teag/.teaz` 本来就是 ZIP 容器。22 个容器共有 **21,068 个条目**，ZIP 头和目录记录合计
约 **2.694 MB**，占整个角色目录约 12.3%。对象和地图的数据正文也已经过压缩：例如地图类
正文约 15.065 MB，压缩后约 1.612 MB，不能把未压缩大小当作可直接节省的磁盘空间。

物品类有 11,532 个条目，是主要组成部分。这包含堆叠物品的独立对象、恶魔种子等合法状态，
数量多本身不说明可以删除。历史区域也保存回访时的地图、物品和任务状态。

## 最合适的方案：缩短对象条目名称

原版 [Savefile.getFileName](../../../../game/engines/default/engine/Savefile.lua) 为每个对象生成
类似 `mod.class.Object-0x12345678` 的名字。名字同时出现在：

- ZIP 的本地文件头和中央目录；
- 对象正文的 `setLoaded(...)`；
- 其他对象的 `loadObject(...)` 引用。

读取时，条目名用来定位对象；真正的类名通过正文中的 `__CLASSNAME` 获取。
[class.load](../../../../game/engines/default/engine/class.lua) 不依靠 ZIP 文件名的类名前缀。

原型只替换已识别的 `getFileName`：一个 Savefile 内为对象分配并记住短十进制编号，
根条目继续叫 `main`。原 native serializer、ZIP 写入线程、DEFLATE 4 级、保存回调、
游戏字段和读取格式都保留。命名缓存位于保存器之外，不写入角色或地图。
减少字符串生成、正文长度和 ZIP 文件名长度，是减少工作量的方向。

### 完整游戏的五组测量

基线为 **Faster 0.2.9**；实验版只增加短编号原型。每次从同一源存档恢复新 home，
每个进程只进行一次普通保存。五组顺序交替，另设预检，预检不计入正式结果。

环境为未经修改的 Linux ToME 1.7.6、内嵌 LuaJIT 2.0.2、Ryzen 7 9800X3D、Xvfb/llvmpipe。
画面为 1280×800、Shockbolt、30 FPS；已有 FBO 保护、同步快照刷新和快速 PNG 保持开启。
两边均关闭联网和角色资料上传，使用正常后台保存及原 GC 策略，没有 debug profiler 或 native preload。

| 指标，中位数 | 原编号 | 短编号 | 观察结果 |
| --- | ---: | ---: | --- |
| `game.teag` | 2,666,804 bytes | 2,480,460 bytes | **小 6.99%** |
| 主档对象条目数 | 2,864 | 2,864 | 相同 |
| 同步保存调用 | 159.62 ms | 157.10 ms | 基本持平 |
| 保存完成总时间 | 515.69 ms | 487.16 ms | **短约 5.53%** |

总时间从 `Game.saveGame` 入口计到 `SavefilePipe.doThread` 返回，包括压缩线程完成反馈、
存档检查和完成回调。所有五组的总时间均缩短，配对差值为 -7.23、-11.36、-29.61、
-43.21、-57.60 ms。

同步调用有一组增加约 3.4 ms，其余四组减少。编号生成发生在后续序列化阶段，
因此前段几毫秒的变化不应归因于短编号加速了快照；当前证据支持“没有稳定回退”，
不能保证任意机器、任意存档的每一次调用都绝不变长。

保存前后检查的回合、位置、生命、角色与背包状态相同。原版和短编号各取一份结果，
在另一个进程关闭命名原型和 Faster 的加载队列优化，用原 `Savefile.loadReal` 成功重载，
无 Lua 错误，重载过程也未改写存档文件。

预检最初把重载后的实体 UID 数值变化视为失败。普通编号对照也出现同样的 205 项变化，
且没有其他检查字段差异；源码 [Entity.loaded](../../../../game/engines/default/engine/Entity.lua)
明确在每次加载时分配新 UID。正式重载检查因此比较 UID 的一一映射和重复引用关系，
其他字段保持严格对照。这是已记录状态子集的验证，不能替代任意 addon 的完整对象图回归。

### 整个角色目录能省多少

对现有 22 个容器做离线、可逆的条目和引用重命名，仍用原来的 4 级压缩：

| 范围 | 原大小 | 短编号估算 | 减少 |
| --- | ---: | ---: | ---: |
| 现有主档 | 2.663 MB | 2.477 MB | 6.95% |
| 整个角色目录 | 21.908 MB | 20.479 MB | **6.52%，约 1.429 MB** |

离线转换只改实际的 `setLoaded/loadObject` 名称，不触碰字符串和函数字节码内容；
反向还原后，每个条目的原始字节完全一致。4 级重压缩的原始数据大小也与原 ZIP 一致。
这是对现存文件逐一改名的估算，不是所有区域已经经过游戏内重写的结果。

**普通保存不会重写所有历史区域。** 立即缩小的是主档，约省整个目录的 0.85%；
区域档在以后正常保存时才能逐步获得收益。为了立刻兑现 6.5% 而强制重写所有区域，
会增加额外保存工作，不符合本次约束。旧长名称档案和新短名称档案可以分别读取，
无需为改名做一次全目录迁移。

## 其他方案如何判断

### 提高压缩等级：不适合这个目标

引擎 [src/serial.c](../../../../src/serial.c) 的后台 writer 将压缩等级固定为 4，
现有 Lua serial API 没有直接调整参数的入口。用实际主档正文在内存中对照系统 zlib：

| 等级 | 压缩数据大小，未含 ZIP 头 | 压缩 CPU 中位数 |
| --- | ---: | ---: |
| 4，原设置 | 2,296,903 bytes | 61.88 ms |
| 6 | 2,236,272 bytes | 79.01 ms |
| 9 | 2,227,106 bytes | 114.51 ms |
| 4，短编号正文 | 2,239,481 bytes | 59.30 ms |

4→6 只节省主档约 2.3% 的总文件体积，压缩 CPU 却增加约 28%；4→9 更不划算。
这些数据不含序列化、CRC、ZIP 头、磁盘和调度，所以不是完整保存时间，但足以排除
“提高压缩等级没有成本”的假设。短编号在保持等级 4 时已获得相近的正文压缩收益，
并额外减少文件头。

### 清理失效引用、重构堆叠物品：有潜力，需要单独证明

旧分析确认过 Fearscape 捕获者、过期背包归属等保留引用。准确清理不再需要的图，
可能同时减少复制、序列化和磁盘内容；但这次没有测出新的体积/总时间收益，不能计入上述百分比。
错误地清掉仍参与技能或回访状态的引用会改变游戏，因此应按具体字段和生命周期验证。

堆叠物品的紧凑存储、将多个对象组成共享压缩块，可能获得比短编号更大的收益。
它们涉及对象身份、引用关系、读回重建，甚至新的序列化和加载布局；当前 C 序列化器
没有把生成的字节交回 Lua 后再成块提交的接口。实现后还须比较新的编码成本与节省的工作，
目前不能断言满足“不增加存档时间”。

截图和日志合计只占约 2.3%，优先级较低。现有快速 PNG 是为降低截图编码成本而采用的方案，
回调更高压缩等级也必须重新测时间，不能用已经取得的速度收益抵消新功能的回退。

## 0.2.10 的正式实现和验证边界

[正式实现](../overload/engine/FasterSaveNames.lua) 只安装在已识别的 ToME 1.7.6
`Savefile.getFileName/init/close` 上，未知覆盖保持原样。同一保存器中的对象获得稳定的十进制编号；
不同对象不重号，当前根始终为 `main`。不同保存器的编号独立，成功初始化和关闭都会释放旧缓存。
缓存的保存器键、对象键都是弱引用，缓存值不反向引用这些键；角色和地图上不增加保存字段。

在设置中使用 `config.settings.faster_tome.compact_save_names=false` 并重启即可禁用。
已生成的短编号档案仍可由原版读档器读取。主档、世界和区域档沿用原本的保存时机，
不会提前遍历或重写历史区域；原生序列化器、后台线程、压缩等级和 GC 策略不变。

[新增回归](../tests/test_save_names.lua) 在 JIT 开启和关闭时各通过 8,529 项检查，
实际执行固定版本的 C 编码器，再用原版 `class.load/Savefile.loadReal` 读取测试对象图。
覆盖全部测试图字段、循环/共享引用、对象表键、二进制字符串、延迟回调和 coroutine yield；
同时验证不同根/保存器、初始化和关闭、GC 释放、序列化失败后的重新保存、设置关闭、
未知覆盖和重复安装。新功能与原来的保存回调复用在同一测试中组合验证。
完整回归套件通过，包括现有原生截图、遮罩和 FBO 检查。

真实游戏验证使用同一个角色与地图；选择的角色/背包状态在保存前后完全相同，
跨读档时按原版重新分配 UID 的规则检查对应关系。实机只比较已记录的状态投影，
不能把合成测试的完整对象图覆盖称为实机全图验证。Windows、Steam 云保存、其他角色/地图、
第三方覆盖引起的嵌套保存仍未实测。

正式代码的测量、源文件哈希和测试日志另存于
[0.2.10 验证证据](../evidence/faster-tome4-save-names-0.2.10/README.md)。
