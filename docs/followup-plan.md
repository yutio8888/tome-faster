# 后续性能优化：可由 addon 实现的路线

2026-09-12，基于已提交并推送的 **Faster ToME4 0.2.2 / d4dbf77**。本轮按“不限制实现复杂度、保持游戏逻辑”的要求继续测量和分析，产出候选设计与局部原型证据。**后续候选没有默认装入 0.2.2**；安装包仍是经过完整回归和真实存档往返验证的上一轮版本。

存在值得继续实施的 addon 方案。优先从可保持输出不变的文字/遮罩缓存、压缩内存修复入手；保存侧并行量化依赖明确的快照裁剪，然后尝试冻结规则时点的分片保存事务。完整后台序列化也能设计，但现有引擎线程接口不足以直接承接 Lua 图，需要新的协议或配套原生组件。

## 新测量定位的剩余成本

三次独立加载相同原始存档，启用 0.2.2，保留原画质与角色资料设置。详细计时故意不包装 `dumpToJSON`，避免使保守兼容检查回退。下表为三次中位数，单位 ms；数据及测量限制见 [followup-results.json](followup-results.json)。

| 阶段 | 中位数 | 含义 |
| --- | ---: | --- |
| `Game.saveGame` 同步调用 | 206.55 | 保存发起时的主线程停顿 |
| 首次 `Game.cloneForSave` | 112.87 | 位于同步调用内；不能套用充分预热微基准的 73 ms |
| 保存截图 | 50.27 | 含强制重绘和读取画面 |
| `Party.cloneFull` | 35.68 | 即使离线也保留原来的回调与 UID 行为 |
| `Player.saveUUID` | 0.0128 | 离线丢弃输出的优化确实生效 |
| 三次完整 GC 合计 | 106.58 | 发生在同步调用返回后的保存 coroutine 管线；单次最大约 43 ms |

这些项存在包含关系，**不能相加为总停顿**。详细计时本身有开销，跨 coroutine yield 的外层计时还会包含期间其他主线程工作。完整保存收益仍以上一轮六次轻量 A/B 为准：同步调用中位数 **459→205 ms**，流程 **912→620 ms**。

新增动作回放中，60 次普通移动没有出现超过 50 ms 的显示回调间隔，最大 43.27 ms。战斗含接敌移动，共完成 51 次动作后按低生命值阈值正常停止；最长显示间隔 67.36 ms，动作响应最长 102.68 ms。快捷栏绘制在战斗 58 帧中累计 141.86 ms，单次最大 14.90 ms。此处显示间隔与玩家输入到屏幕的完整延迟不是同一个指标，寻路、动画和行动回合数也不同。

环境仍为 LuaJIT 2.0.2、Ryzen 7 9800X3D、llvmpipe 软件渲染，不能直接推断用户 Windows 硬件 GPU 的驱动表现。

## 按收益证据和一致性约束排序

| 优先级 | 方案 | addon 实现方式 | 当前证据及下一道验证 |
| --- | --- | --- | --- |
| 1 | 修复角色资料 gzip 的原生内存泄漏 | 在已知导出路径使用自带 lzlib 的同参数 gzip，并检查返回状态、保持调用返回约定 | 已复现每次约 262 KiB 保留；替代接口真实资料输出字节相同。接下来做独立安装器、长时重复导出及多平台检查 |
| 1 | 快捷栏不变文字的纹理缓存 | 对已知快捷键标签缓存光栅化结果，继续每次执行可用性、冷却、鼠标和拖拽逻辑 | 当前绘制热点持续出现；需统计 font draw 占比、逐像素对照与字体/缩放/按键变更失效测试 |
| 2 | 地图特效遮罩缓存 | 复用相同可见格子集合生成的静态 mask FBO，动态 shader 和最终绘制保持逐帧运行 | 直接针对已有 FBO 热点；需有界缓存、完整失效及图像序列对照，收益尚未实测 |
| 2 | 只保留保存消费者依赖的根快照 | 从 Game 根字段建立保存/导出/hook 的依赖闭包，所保留子图继续完整复制，未知扩展回退 | 可同时减少复制和 GC；尚需实际可达性统计及特殊引用差分，不能按字段名猜测删除 |
| 3 | 保存事务切片与 GC 调度 | 冻结同一规则时点，显式栈复制与可恢复进度；分阶段推进增量 GC | 可以争取降低最长连续停顿。必须处理显示写入、弱表、终结器、退出和第二次保存；LuaJIT atomic GC 仍不可拆 |
| 3 | 在线描述缓存或分片导出 | 保存不可变输入或在同一冻结事务中执行；按全部描述依赖失效，保留导出事件 | 原完整导出路径中约 200 ms 的描述工作仍有空间；不能让异步导出读取不断变化的 live game |
| 4 | 定制序列化与后台写入协议 | 兼容 encoder、标准 ZIP writer；更进一步用只接收不可变字节的独立 worker | 现有后台线程只压缩和写盘。完整路线可行，但需明确队列协议、故障恢复、三平台与云保存验证 |

完整论证分别见 [渲染方案](render-next-analysis.md)、[Party / GC / 在线导出方案](save-next-analysis.md)、[快照与序列化方案](snapshot-next-analysis.md)。这里按可独立交付的工作排序，不以“实现复杂”本身否决更深入方案。

## 已实证的新问题：原生 gzip 状态未释放

固定引擎 `src/core_lua.c:4034` 的 `lua_zlib_compress` 调用 `deflateInit2` 后，只释放输出缓冲；成功与失败路径均缺少 `deflateEnd`。另外，输出缓冲估算 `len * 1.1 + 12` 不足以覆盖某些短输入的 gzip 头，测试中 0–64 字节样例返回 nil。

引擎已经包含另一接口 `zlib.compress(data, 9, 8, 31, 8, 0)`：同样使用 level 9、gzip、memLevel 8 和默认 strategy，动态收集输出并执行 `deflateEnd`。在同一个真实引擎中，以 256 KiB 合成数据做两组各 100 次调用，并在计数前后完整 Lua GC：

| 接口 | 每 100 次保留的 native 分配 | 每 100 次时间 |
| --- | ---: | ---: |
| 原 `core.zlib.compress` | 两组均 26,817,600 bytes，约 25.6 MiB | 53.73 / 54.73 ms |
| 同参数 `zlib.compress` | 两组均 0 bytes | 52.96 / 52.69 ms |

内存指标为 glibc `mallinfo2.uordblks + hblkhd`，不是 Lua 堆大小，也不是操作系统 RSS。原接口成功的三种大小样例，压缩字节与候选一致；另将实际角色的 **263,388 bytes JSON** 用候选重压缩，字节仍完全一致。模拟在线导出的测试拦截了全部网络发送，角色选定状态、UID 及 Lua RNG 检查通过。

这是确定的原生内存保留问题，单次 CPU 耗时并不大。不能据此断言它造成了当前每一帧卡顿。0.2.2 的离线优化已经绕过该调用；在线正常导出仍值得修复。将候选投入生产时，要只替换经过验证的路径，保留压缩失败处理和单返回值约定，并验证其他平台绑定的 gzip 参数与状态码。

## 不改游戏逻辑需要保持的关键行为

Party 导出清理明确会调用随机抽样和随机遍历，不只是可能有副作用：`Actor.stripForExport → removeEffectsSustainsFilter → rng.tableSample / tableSampleIterator`。即使把所有效果都选中，抽样与遍历仍会消耗 RNG。删除这段、换一种遍历顺序，或跨战斗回合延后，会影响未来战斗随机数；可优化分配和复制，但须保留调用与顺序。

同理，`map.changed == false` 不表示整个画面静止；动画、粒子和原生绘制回调仍会推进。缓存应落在已证明不变的文字或遮罩上，不能直接冻结整幅地图。未来验收要比较连续帧与后续确定动作结果，不能只检查一张截图或一次存档能否打开。

调低保存 ZIP 压缩等级虽然可实现，代理实验只看到等级 4→1 节约约 8.69 ms，压缩数据增大 4.63%，主要影响后台完成时间。因此它排在快照、GC 和渲染缓存之后；该代理实验不是完整游戏保存 A/B。

本轮诊断与原型保存在 [evidence/faster-tome4-followup](../evidence/faster-tome4-followup/README.md)。原上传存档保持不变；候选收益会分别实测，不把多个嵌套热点的耗时相加当作可兑现的总收益。
