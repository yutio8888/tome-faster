# 0.2.3：删除未使用的导出 Party

2026-09-13。本轮采用新的约束：不要求保留保存时的 RNG 消耗。实现位于 [FasterExportCleanup.lua](../overload/engine/FasterExportCleanup.lua)，不再创建最终未使用的临时 Party，也不再执行它的 `stripForExport`。当前版本仍使用完整游戏快照和原存档格式。

原 `Game.saveGame` 在生成游戏快照后，又对 `game.party` 执行一次 `cloneFull`，清理副本的技能和状态，最后却调用 `game.player:saveUUID(nil)`。该调用不使用刚生成的临时 Party。0.2.3 删除这段临时对象构造、UUID 赋值和清理，保留分数记录、快捷栏更新、游戏与 World 保存队列、玩家控制切换、`_G.game` 上下文切换、导出条件、`saveUUID(nil)` 和外围 `pcall`。

删除的块原本会分配临时实体 UID、创建/清理显示资源、调用效果回调并消耗 RNG。这些副作用也被删除；不为保持旧的随机序列而补做随机调用，不为填补临时 UID 空洞而制造对象。现有角色和物品的 UID 不会被重编号，游戏规则代码没有被替换，但保存之后的随机结果不要求与旧版逐次相同。

## Cults 与自定义扩展

当前存档启用了 Cults。其 `Game.saveGame` 外层包装器禁止在 S.M.A.C.K 竞技场保存，并提供取消战斗的确认框。直接替换这个外层方法会绕过游戏限制，因此安装器只处理两种已识别入口：

- 固定 ToME 1.7.6 本体保存方法；
- 固定 Cults 包装器，且其名为 `saveGame` 的 upvalue 仍指向上述本体方法。此时只替换该内层委托，保留原包装函数、弹窗和回调。

未知包装器、未知内层委托或其他来源/行号布局均保留原实现。重复安装不创建多层包装，后续内层被其他 addon 修改时也能回退。来源与行号检查是兼容性检查，不是代码哈希认证；测试另对所用 Cults fixture 校验完整文件 SHA256。

当前九项 addon/DLC 组合没有发现需要保留的额外业务写入。自定义 `cloned`、`stripForExport` 或技能清理回调若依赖这次临时 Party 构造，需要关闭该项后单独验证。设置 `config.settings.faster_tome.unused_party_cleanup = false` 并重启，可恢复原准备过程。默认启用；其他 0.2.2 开关不变。

## 三组真实保存对照

固定 ToME 1.7.6 / LuaJIT 2.0.2、Ryzen 7 9800X3D、Xvfb + llvmpipe、1280×800、约 30 FPS，仍为同一原始存档的独立副本。每次重新加载，预热约 2 秒，正常保存。只切换 `unused_party_cleanup`，0.2.2 的快照与离线导出优化两侧均启用。顺序为前/后、后/前、前/后，使用轻量计时。

| 指标，中位数 | 保留临时 Party | 删除临时 Party | 减少 |
| --- | ---: | ---: | ---: |
| `Game.saveGame` 同步调用 | 216.682 ms | 166.506 ms | 23.16% |
| 保存发起至观察到完成 | 672.900 ms | 586.968 ms | 12.77% |
| 每次保存最长显示回调间隔 | 227.950 ms | 174.560 ms | 23.42% |

同步调用三次分别为 216.31 / 218.79 / 216.68 ms，启用后为 166.51 / 166.70 / 165.96 ms。单独的详细诊断确认 `Party.cloneFull` 与 `Player.stripForExport` 调用数都为 0；原本的三次完整 GC 仍然执行。没有改变画质、粒子数量、GC 设置或后台保存开关。

完整流程包含保存 coroutine、后台写盘和观察延迟，不能全部算作主线程停顿。显示回调间隔也不是显示器呈现时间。最初尚未支持 Cults 包装器的试跑按设计回退，未把这些样本混入上述结果。原始各次数据与环境见 [export-cleanup-results.json](export-cleanup-results.json)。

## 状态、导出与存档验证

真实正常保存前后，采集的 **27 个现有角色、203 件背包物品**以及队伍、任务、资源、技能和效果关键状态均一致。检查限定于列明字段，既不声称整个世界逐字节一致，也不比较全局 RNG 或临时 UID 分配器。

另在两个独立游戏快照上分别运行原临时 Party 准备过程和删除后过程，拦截所有网络发送，再模拟有效在线导出。两侧的 **263,388 bytes JSON、标题和标签一致**；只对本体由 `pairs` 生成的集合顺序归一化，保留背包、技能等列表顺序。

这次诊断具体观察到：原临时准备调用了 136 次被监测的 RNG 接口（116 次 `range`、20 次 `float`），分配了 1,743 个临时实体 UID；删除后两者均为 0。这是该次诊断的计数，不代表每个存档的固定值。

旧清理还会通过 `Player.setTarget(nil)` 清空**快照**的目标坐标；删除后快照保留原坐标。固定本体的 Game 保存白名单不写入该目标，当前角色的实际在线导出内容也未受影响。真实 live game 的目标和采集状态保持不变。自定义导出若读取此类临时上下文，应按上述开关回退验证。

清理后的存档已成功重新加载、再次保存；六次对照及重载后档案的 ZIP CRC 均通过，原上传 ZIP 的 SHA256 不变。完整回归包括原有测试、91 个克隆差分图、175 项角色导出检查，以及新增 **38 个保存场景 / 824 个断言**；新增场景在 JIT 开启和关闭时均通过，并覆盖真实 Cults 包装器的禁止保存、确认/取消、错误边界和未知覆盖。

测试源码与本地诊断助手见 [验证说明](../evidence/faster-tome4-export-cleanup/README.md)。本轮结论适用于这份存档和所测组合，不包含硬件 GPU 或 Steam 云存档测试；移动与战斗渲染没有在本轮修改。
