# 0.2.11：存档压缩实验、CPU 门槛与原版读档验收

后续 0.2.12 的默认值为库存归属压缩及 Fearscape 清理开启、base62 关闭，见
[当前默认配置](save-defaults.md)。本页保留最初 0.2.11 的实现和验收记录。

2026-09-14，ToME 1.7.6，固定引擎提交
`624a67329fe2ad440c5b344785a9c73fcf22ae63`。

后续已完成 [同一 0.2.11 包的单项开关测试](save-isolated.md)：五个场景各 30 对，
分别测量保存、添加物品及 Fearscape 进入／退出。本页保留最初实现时的混合开关和
不同包对照结果；各单项的影响请使用后续报告，两轮数据未合并。

本轮实现了三项实验：物品归属使用数字 ID、Fearscape 成功结束后清理捕获引用、
base62 对象编号。**三项均默认关闭。** 新增物品后保存的场景通过了 CPU 门槛，
但普通保存场景未能证明新增 user CPU 小于 1%，因此没有将实验提升为默认功能。
0.2.10 的十进制短编号、原版读取器及压缩级别继续保留。

实现和验收没有修改本体引擎。旧档能够加载，实验输出也能由原版读取器读取。
“裸引擎”测试保留了该角色需要的官方 DLC 和读档完成后运行的诊断探针，移除了
Faster 及其他非官方游戏插件；测试副本的 `desc.lua` 同时移除了对应插件依赖声明。
这证明对象数据不需要 Faster 读取器，**不表示缺少插件时原版菜单会自动忽略依赖声明**。

机器可读数据见 [结果汇总](save-compaction-results.json)，逐次数据、固定计划和脚本见
[验收证据](../evidence/faster-tome4-save-compaction-0.2.11/README.md)。

## 实现范围

| 实验选项 | 做什么 | 生效时机 | 默认值 |
| --- | --- | --- | --- |
| `compact_inventory` | 将受认可的 `in_inven.id = inventory_table` 改成原版已支持的数字 ID | 原入包回调链全部完成后 | `false` |
| `fearscape_cleanup` | 清除已成功结束捕获的目标上的 `demon_plane_trapper` | 原 Fearscape 返回流程成功完成后 | `false` |
| `compact_save_names_base62` | 将十进制内部对象编号换成更短的 base62 字符串 | 正常写入当前存档时 | `false` |

这些是实验配置，修改后需重启。可分别启用，无须三项同时开启：

```lua
config.settings.faster_tome = {
    compact_inventory = true,
    fearscape_cleanup = true,
    compact_save_names_base62 = true,
}
```

只有显式 `true` 才启用。省略上述字段或设为 `false` 均关闭；默认 Game 启动路径
不会加载或安装库存、Fearscape 两个实验模块。`compact_save_names=false` 仍能关闭
整个短编号写入功能，包括 base62。关闭写入优化不会替换读档器。

### 物品归属

[FasterInventory.lua](../overload/engine/FasterInventory.lua) 只处理原版标准库存和普通的
`{actor=owner, id=inventory_table}` 归属记录。数字库存 ID 本来就是原版 `getInven` 支持的
形式，避免将整张库存表嵌入每个新增物品的归属记录。

安装器核对固定版本的 Inventory、Actor、Player 三层 `onAddObject` 和 `getInven`。
包装器先完成原始回调链，包括天赋、成就、快捷栏和其他正常业务，然后在最外层
调用结束处处理仍然有效的记录。回调执行期间仍看到原来的库存参数和归属表。
数字或字符串参数直接沿用原方法；自定义元表、归属扩展字段、未知方法覆盖和回调中
发生的转移、删除或替换均保留原行为。

没有保存前全图扫描，没有 `loaded()` 迁移，也不修复旧档中已经脱离当前库存的历史
`in_inven.id` 表。现有堆叠物品不会被删除或合并；只改变符合条件的归属 ID 表示。

### Fearscape 引用生命周期

[FasterFearscape.lua](../overload/engine/FasterFearscape.lua) 保留原版进入、死亡包装器及
退出流程的顺序。只有观察到本次原版捕获，且源楼层、目标、施法者和回调身份均符合
条件，才会在原退出回调的末尾考虑清理。目标必须活着、正常放回原楼层、恢复其原死亡
回调，并已解除维持。原有移动、地面物品回收、其他 NPC 死亡及地图重建工作照常完成。

目标死亡、放置失败、退出报错、未知覆盖、捕获已被替换等情况保留原引用。没有新增
第二个清理 tick，也没有给 Actor 写入新的 addon 死亡闭包。旧档中的已结束捕获缺少
完整的现场证明，安装时不会直接删除它。该修复不会普遍清空地图、AI 记忆或寻路缓存。

### base62 名字

[FasterSaveNames.lua](../overload/engine/FasterSaveNames.lua) 使用
`0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ`，保留根入口 `main`。
计数结果恰好为 `main` 时使用 `_main`，下划线不属于编码字母表，因此不会撞名。
标识符是原读档器使用的字符串键，无须解码或自定义类。

每个 Savefile 的弱缓存、原生序列化器、对象遍历顺序、归档写入器和压缩级别保持既有
逻辑。默认继续调用十进制转换，也不会创建未启用的 62 项字符表。未重新保存的历史
区域归档保持原样，没有后台重压缩或强制迁移。

## 固定 CPU 验收

三组分别在开始前冻结包、脚本、源存档、顺序和样本数，每组 **30 对、60 次保存**。
奇数组 AB、偶数组 BA，每次从相同旧档恢复到独立测试 home；全部有效样本保留，
不剔除慢样本、不扩样，也不合并不同场景。三组合计 180 次保存全部完成，ZIP CRC
检查和选定状态比较均通过。

基准都是最终交付的 0.2.10 包。第一组候选开启 base62 和两项事件优化；第二组关闭
base62、仍开启两项事件优化，执行普通暂停保存；第三组使用第二组的同一个候选包，
但在两边都通过原 `Player:addObject(inventory_table, object, true)` 加入 24 件标准宝石
后保存。第三组的加入过程在计时开始之前完成。

运行环境为 Linux x86-64、内嵌 LuaJIT 2.0.2、Xvfb/llvmpipe、1280×800、Shockbolt
64×64、30 FPS、背景保存。FBO 保护和 500 ms 受击方向提示限制保持默认开启；
内置 profiler、联网和角色上传关闭。没有同时运行其他自建游戏或性能测试。

主指标是从调用 `Game.saveGame()` 前，到保存线程返回且 pipe、waiton、saving、on_done
全部完成时的 **`getrusage(RUSAGE_SELF).ru_utime`** 差值。它包含主线程、保存线程以及
该时间窗内工作的渲染和粒子线程，不能用只测主线程的时钟代替。同步主线程 user CPU
单独记录为次指标；system CPU 和 wall time 也保留在逐次结果中。

门槛预先定义为：对 30 个配对的 `log(candidate / baseline)` 计算均值，使用 df=29
的 Student t 单侧 95% 上界，**上界必须严格小于 `log(1.01)`**。点估计小于 1% 本身
不算通过。该推断限于本次输入和宿主，也依赖配对对数比均值的近似分布假设。

| 组别 | 基准平均 user CPU | 候选平均 user CPU | 配对几何均值变化 | 单侧 95% 上界 | 判定 |
| --- | ---: | ---: | ---: | ---: | --- |
| base62 + 两项事件优化，普通保存 | 1247.031 ms | 1263.732 ms | +1.308% | +2.645% | 未证明 |
| 十进制 + 两项事件优化，普通保存 | 1206.475 ms | 1214.267 ms | +0.631% | +1.550% | 未证明 |
| 十进制 + 两项事件优化，新增 24 件物品后保存 | 1227.525 ms | 1215.696 ms | −0.974% | +0.086% | 该场景通过 |

同步主线程 user CPU 的配对变化依次为 −1.417%、−0.564%、−0.686%，对应单侧上界
为 +0.795%、+1.473%、+1.544%。这些次指标不能替代全进程主指标，也不能把第一组
包装成 CPU 门槛已通过。

独立诊断发现第一组平均全进程 user CPU 增加 16.701 ms，而主线程 user+system 合计
减少 4.676 ms。其他线程 user+system 合计增加 19.657 ms，但其中包含保存线程、
渲染线程及原引擎的粒子线程，不能全归因于 GL 或名字编码。独立压缩代理实验仅测得
约 0.220 ms 的压缩 CPU 增加；它没有覆盖完整游戏流程，不能推翻正式失败结果。
详见 [失败分析](../evidence/faster-tome4-save-compaction-0.2.11/failure-analysis.md)。

**发布处置：三项新实验全部默认关闭。** 库存场景通过不覆盖普通场景的未证明结果。
最后只修改显式启用的入口条件及说明，重新验证开关、行为和兼容性；最终默认关闭包
没有额外执行 CPU 验收队列，因此不能借用此前开启实验的候选数据声称自己已通过。
也没有用重复测试直到偶然通过的方式放行。

入包和 Fearscape 进入/退出的事件 CPU 未纳入这些保存计时，尚不能声称它们自身满足
1% 门槛。Windows、硬件 GPU、其他角色和长时间运行也未在本轮测量。

## 实际缩小了什么

以下为每组全部 30 次主档 `game.teag` 的中位数，差值取两个中位数之差。
它们描述开启实验的候选，不是最终默认关闭配置的新收益。

| 场景 | 基准主档 | 候选主档 | 减少 | 条目数变化 |
| --- | ---: | ---: | ---: | --- |
| base62 普通保存 | 2,480,461 B | 2,463,161.5 B | 17,299.5 B，0.697% | 2864 → 2864 |
| 十进制普通保存，没有新入包/退出事件 | 2,480,463.5 B | 2,480,459.5 B | 4 B，视为无实质变化 | 2864 → 2864 |
| 十进制，新增 24 件物品后保存 | 2,517,738.5 B | 2,492,812.5 B | 24,926 B，0.990% | 2888 → 2888 |

库存场景未压缩数据从 6,029,375 B 降至 5,909,783 B，减少 119,592 B。
对象条目数相同，缩小来自归属记录表示，没有删除新增物品。无新事件的普通场景中
未压缩字节完全相同，几字节的压缩输出差异不计作有效优化。

另外，真实游戏中的一次“进入 Fearscape → 施法者死亡 → 原回调带目标返回 → 保存”
对照中，主档从 **2,337,677 B 降至 2,335,939 B**，减少 **1,738 B、1 个 NPC 条目**。
目标活着，回到原楼层，两个原死亡回调身份恢复；场景内放置的地面标记物保持同一对象，
返回后恰好一份，原有库存和地面物品保留。未手动清除捕获者引用或推进游戏回合。

这个 NPC 使用无行动 AI，实验没有证明整张 Fearscape 地图因本修复被释放。
探针中旧 `astar_map_present` 检查的字段也不等于原版实际的
`ai_state.safe_grid.Astar.map`，因此该标志被排除出结论。进入新捕获时两组都会替换
旧捕获引用；不能把共同缩掉的历史数据算成本修复收益。

这些变化没有立即重写约 21 MB 存档目录中的所有区域。引用仍被其他合法对象持有时，
相关对象也不会消失。本轮未实现跨对象块压缩、自定义读档器或旧图全量清理。

## 兼容性与测试

最终源码的完整回归通过，包括原生 C 序列化、原版读取器、FBO/截图和原有保存功能。
关键新检查及 JIT 关闭复测结果如下：

| 检查 | 结果 |
| --- | --- |
| 十进制/base62/原名，原生写入与原版完整测试图读回 | 32,788 项通过，JIT 开/关均通过 |
| 库存原回调差分、堆叠/装备/转移/丢弃、别名、未知覆盖与 GC | 28 个差分场景，455 项通过，JIT 开/关均通过 |
| Fearscape 原进入、主动/死亡退出、回调身份、失败与旧引用保留 | 69 个场景，2,699 项通过，JIT 开/关均通过 |
| 实际 Game 启动、默认不加载、独立显式开关与原保存/加载路径 | 89 项通过，JIT 开/关均通过 |

最终包另完成 9 次真实游戏验收：默认保存及原版读回；三实验全开后加入物品、保存、
原版读回、0.2.10 的原读取器读回、再次保存及原版读回；三实验全开后的真实 Fearscape
死亡退出保存与原版读回。默认路径的两个原事件方法保持原源码，两个实验模块未加载；
第 62 个试验名字仍为 `62`，三实验开启时为 `10`。

所谓原版读回使用未修改的 1.7.6 引擎和 stock `Savefile.loadReal`，运行目录中没有 Faster
源码或包。最终该目录的 addons 只保留官方 Possessors 和诊断探针，另保留原档所需官方
DLC；原始串行化归档未改写，仅测试副本 `desc.lua` 的非官方依赖列表被调整。
读取后数据、库存顺序与 UID 引用别名比较通过。原版加载会重新分配 Entity UID，因此
比较使用一一映射，不能把原始 UID 数字相等当成正确性要求。

真实旧档验收比较的是选定状态投影，不是逐字段证明整个真实存档图相同。完整图差分
发生在原生序列化测试夹具中。源码身份保护和这些检查也不等于任意第三方插件组合保证。

早期预检出现过两个诊断问题：库存验证最初未归一化 owner UID、按重新分配的 UID 排序；
Fearscape 探针最初在强制重绘中重入场景步骤。前者只导致状态比较误报，后者导致一轮
预检超时。均保留原记录，修复诊断后使用新会话完成；它们没有进入任何正式 30 对队列，
也没有用生产代码修改掩盖。详见证据说明。

## 后续放行条件

库存场景已有节省字节且保存 CPU 不劣于门槛的证据，但普通场景的上界仍过宽。
下一轮应先减少完整进程计量中的宿主和线程噪声、确定一次固定且有足够区分力的协议，
再重新评估默认启用资格，同时补上真实入包、退出事件的 CPU 计时。不能直接换用较好看的
次指标、删慢样本、合并不同工作负载，或重跑同一个小样本队列直到通过。

可能需要新读取布局的块压缩保持未实现状态；在具备旧档与裸引擎兼容方案前，不作为
默认优化加入。旧存档引用迁移同样需要独立、可证明不会丢失游戏对象的适用条件。
