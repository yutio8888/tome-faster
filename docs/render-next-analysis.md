# 移动与战斗渲染：下一阶段 addon 优化分析

基线为 ToME 1.7.6（本体提交 `624a67329fe2ad440c5b344785a9c73fcf22ae63`）与 tome-faster 0.2.2（`d4dbf77`）。这份报告只做源码分析，未运行新原型，也没有修改交付代码。复杂度不作为排除理由；候选必须保留游戏逻辑、实际显示内容和动画推进规则。

**优先做热键文字纹理缓存，然后试地图特效遮罩缓存。** 前者有持续的 CPU 热点证据，改动边界清楚；后者可能减少整视口渲染工作，但仍保留动态特效的最终绘制，不能据此承诺消除全部 NativeGL 长帧。整帧脏标记缓存和直接减少粒子更新次数不满足语义要求。

## 1. 热键栏：只缓存确定的文字纹理（优先级 P1）

入口是 `E/HotkeysIconsDisplay.lua:133` 的 `display()`，上层为 `M/class/uiset/Minimalist.lua:1780` 的 `displayHotkeys()`。`display()` 已经以 `actor.changed` 控制重建，但移动、战斗会频繁设置它。每次重建都在第 247、252、266 行重新执行按键标签或冷却数字的 `font:draw()`；同一按键标签几乎不会随回合改变。

这不是已有字号测量缓存能够消除的工作。`E/utils.lua:1452` 附近缓存字体实例、1472 附近缓存文字尺寸；`src/core_lua.c:980` 的 `sdl_font_draw` 仍创建 SDL surface，`font_make_texture_line:886` 仍生成新纹理并经 `make_texture_for_surface:270` 上传像素。复用相同的最终纹理，可以同时减少文字栅格化、GL 上传和随后回收旧纹理的工作。

建议实现一个专用有界缓存，并在识别出的原版 `display()` 内仅替换上述三个栅格化调用。保留原方法的其余语句、调用次数和顺序；不在全局覆盖所有字体的 `draw`，也不把字体 userdata 换成代理。字体实例由其他 UI 共享，粗体/普通体切换本身也必须保持原有顺序。

- 缓存键至少包含字体实例、当前字体样式、实际字符串、宽度、RGB、换行和 UID 绘制选项、字体重建代次、引擎断字策略。按键配置变化自然形成新字符串；换字体、缩放和重新加载显示资源时清空旧代次。
- 第一版仅接受这里产生的普通按键文本和冷却数字。包含动态 UID/实体、可执行扩展或未知字体方法的文本走原实现。颜色控制码也必须按真实参数与解析规则处理，不能用去掉格式后的文字做键。
- 缓存纹理及不变尺寸；每个调用返回独立的小元数据表，避免第 253 行写 `gtxt.fw/fh` 或其他调用者修改结果时污染缓存。只共享原生纹理资源，不共享会被修改的返回表。
- 缓存放在模块内，使用明确的条目或字节上限，避免进入 `game` 的存档对象图。弱 owner 键对应的缓存值不能反向强引用 owner；不能依赖弱值表保住跨回合命中率。
- 完整保留 `preUseTalent`、冷却和资源查询、物品查找、`getObjectCooldown`、布局和鼠标命中表更新。这些不是纯函数的通用保证，缓存其结果可能改变 hook、资源可用性或副作用。

`toScreen():292` 继续逐帧绘制实体图标、冷却角度、悬停状态、边框、阴影和文字；动画 shader 的执行时机不变。禁止把整份 `items` 长期复用当成“相同热键”。

验证分两层：先统计三个调用点的次数、命中率、文字生成 wall/CPU 和纹理上传量；再对相同输入做原版/候选像素与返回结构差分。覆盖普通/粗体、中文键名、改键、冷却 0/1/多位数、物品耗尽和替换、多个角色、翻页、拖动、缩放、阴影开关及兼容性回退。使用带调用计数和副作用的假技能/物品方法，确认业务调用序列完全一致。集成时检查同一帧后续 GL 状态和动画输出，不能仅凭静态截图通过。

## 2. 地图特效：缓存原始遮罩，逐帧执行动态合成（优先级 P2）

入口是 `E/Map.lua:1197` 的 `displayEffects()`。每个 z 层在 `zDisplay():624` 中先执行 `calcEffectVisibility():1181`、粒子，再执行特效。对于带 `effect_shader` 的可见特效，原版每帧执行：

1. 清空整张视口大小的 `Map.fbo` 为透明。
2. 遍历 `e.seen_grids`，把每格同一遮罩图块画入 FBO。
3. 绑定当前特效纹理，通过 `target_fbo` shader 把遮罩合成到主场景。
4. 按 `nb_keyframes` 推进 `effect_shader_tex.cnt/cur`。

当范围、可见格子和坐标不变时，第 1、2 步重复生成同一张纹理；第 3、4 步仍可能随时间改变。候选只省去重复的遮罩生成，保留每帧的可见性计算、特效过滤、原顺序最终 shader draw 和动画计数。它不减少伤害判定、持续时间更新或粒子更新。

建议先实现保守的精确匹配缓存，再考虑脏标记：

- 缓存输入为本次实际遍历的有序格子坐标，以及真实图块纹理、overlay 参数、`mx/my`、瓦片尺寸、缩放、视口尺寸和显示资源代次。不要只比较 `e.grids` 表身份；它可能原地修改。不要使用存在碰撞却没有逐项复核的哈希。
- 第一版仍完整执行 `calcEffectVisibility()`，比较其结果，不按 `map.changed` 跳过。该方法会重建 `e.seen_grids` 并设置 `e.seen`；不能顺便改变 Lua 中零、false、nil 的原有处理。若后续用可见性代次替代逐格比较，必须覆盖所有原生/Lua 写入口，另行证明完整性。
- 按实际绘制顺序比较格子更保守，避免擅自假设半透明图块在边界永不重叠。外层特效 `pairs` 的遍历和合成顺序保持原样。
- 仅接受确认稳定的原版 `Tiles:get`/纹理绘制路径；未知动态纹理、自定义显示 hook、未识别的 overlay 扩展回退。`E/Tiles.lua:103` 的图块缓存本身不等于整个遮罩已缓存。
- 多个特效不能共用一张“上次遮罩”。使用每张地图有界的 FBO 缓存，按条目和像素字节双重预算淘汰；窗口大小 1280×800 的 RGBA8 遮罩约占 3.9 MiB，实际分配及驱动开销还可能更高。分配失败立即走原路径。
- 缓存完整的原视口分辨率，保持透明清除、过滤、纹理坐标和边界采样。`M/data/gfx/shaders/target_fbo.frag:8` 起会采样周围四角，不能未经验证裁成特效包围盒；缩小 FBO 会改变邻域、坐标和采样边缘。
- 生命周期入口包括 `Map.enableFBORenderer():123`、视口调整、地图切换、特效移除和资源重载。缓存不写入地图、特效的可序列化字段。`Map.processEffects():1258` 和 `removeEffect():1321` 的逻辑保持原样。

兼容性还要检查两个容易遗漏的细节：原版 `Map.fbo` 是公开的临时缓冲区，其他 addon 可能读取或改写它；缓存命中省去 `fbo:use()` 也会省去其模型矩阵重置、清除色等 GL 状态变化（`src/core_lua.c:2779`）。应限定已识别调用链，证明最终状态一致，或显式复现必要状态；不能仅比较 shader 参数。给未知消费者保留原路径，而不是假定公开 FBO 无人使用。

验收需要对多特效重叠、范围移动、持续时间到期、FOV 边缘、地图滚动、震屏、半透明纹理、不同缩放、多个 z 层、目标预览以及纹理动画做逐帧对照。遮罩可以在同一已冻结的绘制输入下分别离屏生成并逐像素比较；最终动态合成要复用同一帧 tick 和 `nb_keyframes`，不能通过再次调用完整 `Game.display` 来制造“同一帧”，后者会再次推进状态。

先记录命中率、遮罩重绘次数、实际 FBO 数量/内存、单次生成和合成耗时，再看端到端长帧。命中仍要运行整视口动态合成，原来的 107 ms `postEffects` 阻塞也可能完全不受影响；这是需实验回答的问题。

## 3. FBO 管线：可研究条件化省去复制，不能直接合并 shader（优先级 P3）

`M/class/Game.lua:createFBOs():662` 创建主场景 A、第二缓冲 B、整个窗口的 full_fbo，并把 A 注册给原生粒子。`displayMap():1868` 的固定顺序是：

```text
地图 / 背景 / 天气 → A
A 复制到 B → 扭曲粒子（读取 A）→ 网格线 / 平滑 FOV
B → 按原顺序 postEffects，A/B 交替 → full_fbo
UI / 对话框等 → full_fbo → gamma shader → 窗口
```

A→B 的复制在没有任何需要读 A 的扭曲粒子时，可能省去：把网格线/FOV 直接画到 A，再交换传给 `postEffects` 的源与临时缓冲。复杂重写本身可接受，但须解决下列真实依赖后才能启用：

1. `core.particles.drawAlterings()` 的待画队列在 C 中，公开 API 没有查询队列是否为空。`E/Particles.lua:53` 的 `loaded()` 能看到已知定义的 `alterscreen`，可以构建保守注册表；但必须覆盖已加载对象、子粒子、存档恢复、直接 native 创建及未知定义。有任何无法证明的活动粒子时回退。只看当前地图 Lua 发射器列表不充分。
2. `src/particles.c:417` 的普通粒子 shader 也会把全局 `main_fbo` 绑定到纹理单元 1；“不是 alterscreen”不代表不读取 A。必须审计其 shader 的真实纹理依赖以及后续目标/UI/自定义图层消费者。改写后 A 的内容可能与原版临时缓冲不同，跨阶段读取也要匹配。
3. `fbo:use(true)` 会清空缓冲；不能先关闭 A，再靠同一个 API 无损重新打开。需要在原来关闭 A 之前插入覆盖层，并保留背景、前景、天气、目标、震屏和声音等调用的原先顺序。
4. 1:1 的复制通常近似原样，但严格验证仍需覆盖 RGBA 精度、边缘采样、透明度、viewport 和 blend 状态。不能把所有 pass 的数学等式当成像素等式。

`src/core_lua.c:2901` 的 `gl_fbo_posteffects` 按传入顺序执行 shader，在每个中间目标和最后目标上清屏，最后恢复 shader/blend。把它直接换成 `toScreen` 会丢失清屏和状态语义；只在全部这些条件证明相同的专用路径上才有意义。`M/class/Player.lua:458` 的 `updateMainShader()` 还按当时表遍历顺序组合特效，不能为了缓存而排序。

多 shader 融合也可研究，但暂不宜作为首个原型：模糊、运动模糊、锐化依赖邻域采样；A/B 中间纹理会发生量化、截断和边界处理。省去中间存储后即使公式相同也可能改变图像。主 shader 的生命/空气/灵能警告、染色、强化以及最终 gamma 都必须保留；“当前生命满”不足以证明整个 shader 是恒等变换。某个已证明恒等的组合可以单独建立快路径，不能用关闭 shader 设置代替。

另一个条件化方向是加载阶段预热已知 shader/FBO 格式组合。只使用独立离屏 quad，不能通过施放技能或生成完整粒子来预热。先证明长帧集中于某个程序的首次 draw，再恢复全部 GL 状态、uniform 和资源生命周期。它主要转移首次使用延迟，不保证降低总工作量；现有证据尚不足以认定冷编译是主因。

## 4. 脏标记能用于局部资源，不能代表画面静止

`E/Map.lua:606` 即使 `self.changed` 为 false，仍先调用原生 `_map:toScreen()`，再清理粒子；后面的早退只跳过标记处理。`src/map.c:1780` 的 `map_to_screen` 仍推进平滑滚动、绘制 sprite 动画、执行 z 回调；`display_map_quad:1615` 附近更新动画，1912 附近处理 `display_last`，1922 附近还可能调用 FOV 更新。直接复用上一帧地图会改变这些行为。

`Game.displayMap():1838` 本身也推进震屏并调用 `rng.range`；`src/shaders.c:35` 的 `useShader` 每次设置真实 `cur_frame_tick`；`src/main.c:652` 的绘制入口在 Lua 显示前通知原生粒子线程推进关键帧。因此，跳过 Lua 绘制、伪造 tick 或减少 `nb_keyframes` 都不是等价缓存策略。

UI 的同类边界：

| 部位与入口 | 可以进一步缓存的部分 | 必须逐帧保留或单独证明的部分 |
|---|---|---|
| `Minimalist.displayPlayer:1518` | 未缓存的固定标签和几何；数值纹理已有缓存 | 角色图像动画、可用点数闪烁、超重警告、布局/鼠标区 |
| `displayResources:731` | 已确认纯文本的最终纹理 | 动态资源 shader、自定义资源 getter/display 回调 |
| `displayBuffs:1283` | 计数文字和固定边框几何 | `iconOverlay`、持续时间、鼠标和自定义效果显示 |
| `displayParty:1411` | 固定框和标签 | 头像动画、生命条、召唤剩余时间 |
| `E/LogDisplay.display:227` / `toScreen:257` | 保留已有文本缓存后再找重复工作 | 按真实时间淡出、嵌入实体、滚动与命中数据 |
| `Minimalist.display:1976` | 局部图元缓存 | 地图绘制、当前时间、各组件调用、viewport padding、GL 变换 |

小地图是较低优先级候选。`src/map.c:1971` 的 `minimap_to_screen` 每帧扫描并上传纹理；可缓存最终小地图，但需要完整跟踪可见/记忆格子、实体 minimap 信息、视口和滚动变化。`map.changed` 在主地图绘制后已经复位，晚到的小地图不能直接拿它判断。当前约 0.12 ms/帧，优先级低于热键；不完整失效会显示过时敌人或探索信息，不能接受。

`E/ui/Base.lua:181` 的 `drawFrame()` 和 `E/utils.lua:2255` 的 `clipTexture()` 还会重复计算九宫格几何并创建临时表。可以缓存完整参数对应的裁剪结果，仍按原顺序发出相同 draw；若把多个半透明图元预合成成一张纹理，则必须重新证明 alpha、重叠和中间精度完全一致。先测几何计算占比，不能从“九次 draw”直接推断显著收益。

## 5. 粒子和原生等待：先区分原因，保留纯 addon 的实际边界

原生粒子确实存在可能阻塞主线程的路径：

- `src/particles.c:266` 的 `particles_update` 更新粒子数组，并在最后一次更新时持有发射器锁；`particles_draw:417` 在第 429 行等待同一锁，而且在锁内执行 `glDrawArrays`，到第 471 行才解锁。
- `thread_particle_run:731` 先运行粒子 Lua updater，再更新原生数组；工作线程循环在 `:1071` 附近还持有整个线程的发射器列表锁。
- 新发射器加入（`:1142` 附近）及 `particles_free:229` 可能等待工作线程列表锁。创建/回收粒子造成的停顿未必出现在 `Map.displayParticles` 内。

这些是源码上的可能原因，不是已测 107 ms 样本的归因。下一轮诊断应把 GL 调用的程序/FBO/线程与 SDL 互斥锁等待关联起来，记录 wall、线程 CPU、调用栈、粒子定义、活动数量和每帧更新次数。用固定大小缓冲收集后输出，避免每次锁等待同步写日志扰动结果；需要区分实际调用符号 `SDL_mutexP`/`SDL_LockMutex`。GL 侧补充纹理上传、程序首次使用、FBO 绑定、完整 pass 次数和可用的 GPU timer。不要在正式性能路径每帧加入 `glFinish`。

仍能通过 Lua addon 做的工作，是优化某个已证实昂贵粒子定义的纯计算，或修复已证明不应存活的发射器/对象引用。每个定义都需差分验证生成随机数的顺序、位置、寿命、数量、子粒子和再次可见时的状态；不能按“当前不在屏幕内”整体销毁再创建。`dieDisplay()` 会丢弃原生发射器，重新 `loaded()` 不是恢复同一粒子时间线。

双缓冲顶点数组、缩小原生锁范围、上传队列或 GPU buffer 改造需要 C 层支持。当前纯 Lua API 没有安全导出/恢复原生粒子数组或更改工作线程同步的接口；用 FFI 越过 userdata 内部布局修改指针会引入版本 ABI 和线程竞争，不能视为可靠的纯 addon 方案。这个边界来自缺少可用接口，与实现复杂度无关。

## 建议实施与验收顺序

1. 对热键栏三个文字调用点做细分统计，同时实现 P1 的独立缓存原型。先通过纯调用序列、返回结构和像素差分，再做轻量回放 A/B。
2. 记录每个地图特效的遮罩输入变化率、重画像素量及生成/合成耗时。如果稳定帧占比足够，实现 P2；逐像素证明缓存前后的遮罩，再验证完整帧和状态推进。
3. 保持生产版本不变，完成带 GL 程序/FBO 身份和锁等待的本地诊断。根据真实瓶颈决定继续减少 FBO pass、预热 shader，还是逐个审查粒子定义。
4. 每个候选独立开关、识别固定本体和已知集成、未知覆盖回退；支持释放缓存及资源重建。不把缓存对象写进保存图，不修改 GC 调度、游戏 tick、战斗规则、FOV 逻辑或动画步长。

正式 A/B 使用同一原始存档副本、相同输入、图形配置和预热策略，至少三组交替；分别报告帧间隔/动作响应分位数、长帧数量、目标函数 CPU/wall、缓存命中与资源占用。保留死亡/低生命停止条件，战斗路径不同就不能把累计耗时直接当等量工作比较。视觉验证应固定绘制输入与时间后做差分，性能测试则恢复真实时间、真实粒子线程和正常帧率限制。通过 llvmpipe 后仍需在实体 GPU 上复测，才能说明用户机器上的实际改善。
