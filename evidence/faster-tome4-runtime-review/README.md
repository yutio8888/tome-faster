## 1. 地图：复用检查源码，不缓存检查结果

证据：`game/engines/default/engine/Map.lua:469-551`，特别是 530-539。
`engine/Actor.lua:245-252` 的实体移动会移除旧格子并写入新格子，分别经 Map 的 remove／call
触发 updateMap；地图生成、显示状态变化也会触发。每格按实体层排序，拼出检查函数源码，
随后才查询 `_check_entities_store[源码]`。编译本来就有缓存，浪费的是重复格式化和拼接。

实现位于 `overload/engine/FasterRuntime.lua`，由 Map superload 安装，并由 ToME:load hook
补足 Map 已被提前 require 的情况。复制固定版本 updateMap，仅替换源码构造块：

- 仍在显示回调之后重新收集层，并调用原 `searchOrderSort`。
- 用层序列索引源码字符串；每个 Map 最多 128 种、每种最多 32 层。超限或未知键走原构造。
- 缓存放在弱键旁表，值不引用 Map，不加入对象图和存档。
- `_check_entities_store` 的查询、赋值仍由原逻辑完成。它被清空时会重新编译，旁表不私存函数。
- 函数每次执行仍从当前格子读取实体，保留短路顺序、回调参数以及三个 FOV 缓存更新。

兼容性边界：只能覆盖已识别的原 updateMap；未知先前包装会跳过，后来 addon 仍可覆盖。
原函数路径／行边界检查不是内容哈希认证。大幅改动本体或自定义 Map 类需要重新核验。

差分测试覆盖标准／额外层、空格、替换实体、检查回调删除后续层、显示回调增加层、
不同遮挡标志、清空编译缓存、越界坐标、源码缓存超限、已加载 Map 与重复安装。
生成源码与原版逐字一致，显示／寻路／检查顺序及参数轨迹一致。

2,000 次相同三层布局更新：构造源码 2,000 → 1；排序和编译次数不变。
关闭图形等成本的真实 updateMap Lua 方法微基准，15 万次更新的三次 CPU 时间：

| 模式 | 原版，秒 | 优化，秒 |
| --- | --- | --- |
| warm LuaJIT | .074575 / .075206 / .075007 | .021429 / .021344 / .021205 |
| LuaJIT 解释执行 | .163149 / .158392 / .158663 | .120044 / .119448 / .119184 |

这是当前主机上的隔离 CPU 测试，不包含真实渲染、地图数据和 GPU，不能换算成整局 FPS 提升。

## 2. Ashes：删除确实未使用的扫描

证据：`ashes-urhrok/tome-ashes-urhrok/data/talents/corruptions/heart-of-fire.lua:116-141`。
文件 SHA256：`9169ec6910a96af6ce469ef88c4b257165955f96ce7828c8508e2d36372a92b5`。

`T_INFERNO_NEXUS.callbackOnActBase` 先作半径 10 投射，遇到受诅咒目标进行 50% 判定，再作
半径 1 投射。每个非空相邻目标都会扫描源目标的 tmp，并计算未被读取的 is_burning。
本轮只删除这五行。**没有按技能说明补上“目标必须燃烧”的条件**；那是机制改动，超出性能修复。

通过 ToME:load 安装，因为 DLC 加载器也在该 hook 中加载技能，且 DLC 权重 2／3／10 小于
本 addon 的 100000。`engine/Module.lua:679-703` 与 `engine/class.lua:406-433` 保持注册顺序。
仅替换匹配来源／行边界的回调；无 Ashes 或遇到未知包装时保留已有行为。

固定夹具包含多个受诅咒目标、普通目标、空格、已触发 turn_proc 的目标、损伤标志、
两种随机结果和延迟施加效果。事件轨迹完全一致；成功传播夹具的效果条目访问 300 → 0。
投射、RNG、伤害、延迟效果和返回值保持原顺序。没有减少投射格子数量或删除粒子。

## 3. 实际尝试后没有纳入的方案

### 蜘蛛机器人索引：遍历更少，但 warm-JIT 更慢

证据：`orcs/tome-orcs/data/talents/spells/terrene-technomancy.lua:83-162`，
SHA256 `3d48fdd5bf72d4c2c6f1479172acc0cfe1e8dae7a3e64b776a398e386cf9f252`。
`countBots` 每机器人遍历机器人表，`hasBot` 又为每个候选目标重复查找。

曾实现比“整回合位置索引”更保守的原型：每次 projectCollect 之后，只在候选筛选期间
构建临时坐标索引，下一个机器人重建。这样能看到投射回调和前一个机器人移动造成的变化。
10 机器人夹具访问 488 → 210，目标、移动、粒子、RNG、伤害、到期和自定义 helper 回退轨迹一致。

但 20 万批、10 机器人／8 候选的纯占位微基准中，二维临时表的 warm-JIT 耗时约为原扫描
4.19–4.26 倍；扁平表也约 2.46–3.05 倍。解释执行更快，不能据此推断游戏的 JIT 路径更快。
因此撤下该原型，生产 addon 没有替换 Spiderbot。后续只有在测到更大实际群体、证明收益并建立
可靠失效通知后，才考虑复用 scratch 索引或维护计数；不能跨投射复用潜在失效的数据。

### 可见性命中键：已有 JIT 路径没有明确收益

证据：`game/modules/tome/class/Actor.lua:7491-7521`。原型只快捷读取默认 `nil/nil` 命中，
其他情况交给原方法，避免改 RNG／onSeen／缓存寿命。100 万次默认命中的 warm-JIT 比率为
.999 / 1.015 / .992，处于微小差异范围；解释执行较快不足以支持增加默认包装，所以保留原版。
