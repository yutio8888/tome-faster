# 最终只读验收审查

本轮只读检查了两组固定计划、运行及分析脚本、冻结候选包、当前生产命名代码，以及已完成的
真实 Fearscape / 无 Faster 读回记录。没有运行游戏、编译、压缩或性能测试；库存组全部
完成后才读取其完整 CPU 汇总，没有根据部分计时判断，没有修改生产代码或冻结工件。

两组计划能支持各自**保存阶段**的“新增进程用户态 CPU 小于 1%”检验；它们不能支持所有
游戏阶段、角色或平台都满足该上限。普通保存组已完整完成，配对点估计 +0.63103785%，
单侧 95% 上界 +1.55005355%，因此仍为 **NOT PROVEN**。点估计小于 1% 不能改判通过。
库存组固定 30 对也已完整完成，配对点估计 **−0.97379416%**，单侧 95% 上界
**+0.08603013%**，按原门槛 **PASS**。其双侧 95% 区间为 [−2.23462501%, +0.30329698%]；
这证明该保存场景满足新增开销的门槛，不等于证明真实 CPU 必然下降。

分析器要求恰好 30 个完整配对，拒绝退出错误、超时、Lua 错误、状态不等或缺少完成记录。
它核对每个变体的生产包 SHA、变体内所有生产源码 SHA、全组相同的诊断源码、引擎和原档，
并核对计划 SHA、执行序号、实际开始时间顺序，以及计划声明早于全部正式会话。
两组分别分析；旧 Base62 默认开启批次不得合并，普通与库存两组也不得互相抵销。

统计定义保持为配对 log ratio：固定 n=30，t(29) 单侧 95% 上界严格小于 `log(1.01)`
才通过。完整记录方差、双侧区间和执行顺序子组，无删值、扩样或重复至通过的逻辑。
库存组的通过只增加一个已验证的库存后保存场景，不能覆盖普通保存的 NOT PROVEN。

计时起点位于 `game:saveGame()` 之前，主指标为 `getrusage(RUSAGE_SELF).ru_utime`；
终点为原 `SavefilePipe.doThread` 正常返回，并断言 `pipe`、`waiton`、`saving`、`on_done`
均已排空。它包含保存窗口内主线程、保存 worker、粒子及渲染等进程线程的用户态 CPU。
同步 `RUSAGE_THREAD` 用户态 CPU 是次指标，不能代替主指标；旧 `clock_gettime(3)` 的
线程 user+system 也不能替代用户态指标。

两组使用相同 probe，且实际 runtime 内 probe 与冻结源文件一致。普通组没有新增物品；
库存组在同一复制存档中调用实际 `Object.new` 与 table-id `player:addObject` 添加相同
24 件标准 gem，并断言物品归属者和预期归属表示。随后才执行 `state()` 和 CPU 起始采样。
因此物品创建、onAdd 回调及归属规范化的即时 CPU **在计时之前**，没有被测成“新增开销
小于 1%”。由事件形成的存档状态，以及之后发生的克隆、GC、序列化和压缩，属于后续保存
计时。不能把保存阶段的结果写成“拾取/装备/物品处理的 CPU 已验证小于 1%”。

Fearscape 真实场景也先完成进入、施法者死亡、返回和回调排空，再开始保存。其事件 CPU
同样未被这次保存计时覆盖。两个 helper 没有每次保存的全图扫描，这是源码事实；没有扫描
本身不是全进程 CPU 已满足门槛的统计证据，也不证明事件处理或游戏启动 CPU 的上限。

当前 Base62 默认关闭的代码没有发现遗漏：`FasterSaveNames` 仅在
`options.compact_save_names_base62 == true` 时调用 `makeBase62()`，未配置、false 或其他
非 true 值都继续使用原 `tostring` 十进制；字母表只在 opt-in 时分配。
`compact_save_names == false` 仍在前面禁用整个紧凑命名安装。根 `main`、弱缓存生命周期、
未知方法保护保持原有逻辑。默认分支不需要 Base62 decoder，旧十进制和已写出的 Base62
文件都继续由原版字符串文件名读取路径处理。

命名生产源码与冻结候选包内 `FasterSaveNames.lua` 逐字节相同。Game、Inventory、Fearscape
三个文件最初也与冻结包一致；在两组完成后的发布收尾中，其启用条件又做了下述保守调整。
README 和 init 描述已明确 Base62 experimental / opt-in，
测试文件同时覆盖显式 Base62、显式十进制和没有 options 时第 62 个名字仍为 `"62"`。
本次仅审阅这些测试代码，没有重跑测试。

已完成的真实 Fearscape `sessions/candidate-check` 使用上述冻结候选包，场景为
`casterdead`：由原 `forceUseTalent`、实际 NPC 死亡和真实游戏循环执行原回调，没有手工
清除 trapper，也没有手动推进 tick。记录证明返回同一个来源 Level 与目标、恢复原双方
死亡回调、原标记物件恰好返回一次，并且 trapper 已清空。保存成功且保存前后状态检查相等。

`sessions/bare-candidate-check` 成功从该结果重新加载，归档文件未变；标记物件仍恰好一件，
来源层描述正确，捕获者引用和 Fearscape 死亡包装保持缺席。该 runtime 中没有 Faster
目录或 teaa，输入源码清单无 Faster，desc.lua 无 Faster 声明，probe 核对了原版命名器和
`Savefile.loadReal`，并断言没有 Faster 模块加载。这支持“**无 Faster 的原引擎读回**”
该真实场景；它保留原存档所依赖的其他 addons，不能称为“去掉所有 addons 的全裸兼容”。
这一真实 `casterdead` 案例也不能代替所有 Fearscape 分支的真实游戏测试；此前的差分
fixture 为其他分支提供独立证据。

基于普通保存组仍未证明门槛，库存组通过后仍采用保守发布处置。已只读核对实际新代码：
`compact_inventory`、`fearscape_cleanup` 两个安装器均要求显式 `true`，Game superload
在 require 之前也分别检查对应字段严格等于 true，使默认路径不加载或安装这两个新模块；
Base62 继续 opt-in。这些独立开关的缺失、false、其他非 true 值和显式 true 启动分支已由
主代理补充测试；本代理只审阅代码，没有重新执行测试。
默认保留原 0.2.10 十进制路径，不宣称有新的默认压缩项通过严格 CPU 发布门槛。
冻结 `0f314…ed01` 包仍是两个事件功能默认开启的被测候选，不能将它的测量
数值标注成默认关闭成品的通过结果。开关调整后的成品属于不同代码和 SHA，最终打包时
应另核对默认/显式开关行为与包内内容，不需要以同一候选随意重跑 CPU 来寻找通过。

进一步精确区分主线程、保存线程、粒子和 GL 的计量可以用于成本诊断，但这会回答更窄的
问题，不能事后替换 RUSAGE_SELF 验收指标。默认关闭新功能会放弃自动取得新增压缩收益，
同时保留明确选择实验功能的入口；这与当前证据相符。只有有依据的新实现或预先声明的新
测量问题，才构成下一轮独立实验的理由，而不是对同一失败候选反复取样。
