# Base62 候选未通过 CPU 门槛：独立成本审查

本次复核保留原来全部 30 对正式样本，没有删值、追加样本、重定义指标或重新裁定通过。
原固定包对照的进程用户态 CPU 配对变化为 **+1.30797%**，单侧 95% 上界 **+2.64528%**，
因此尚未证明新增开销小于 1%。双侧 95% 区间为 **[−0.27866%, +2.91984%]**；
这个区间也不支持“已经证明真实回退大于 1%”的更强断言。

已复核 `tmp/save-compaction-20260914/cpu-results.json` 与全部 60 份 `result.json`。
以下派生指标、子组及区间均为失败后的成本诊断，不能替代原预声明主指标。
可重复的只读脚本和全部逐对结果见 [failure-analysis.py](failure-analysis.py) 与
[failure-analysis-results.json](failure-analysis-results.json)。

主线程和其他线程的账目满足：

```text
Δ进程 user = Δ主线程(user+system) + Δ其他线程(user+system) − Δ进程 system
           = −4.67595 + 19.65655 − (−1.72017)
           = +16.70077 ms
```

因此，本轮新增 CPU 的净差额落在非主线程侧。原版 base62 编码发生在主线程的命名调用内，
而主线程两个区间的净平均值均下降；现有数据不支持把整段 +16.7 ms 直接解释成 Lua 编码成本。
它仍不能排除较小的编码成本被其他主线程变化抵销。同步返回后的主线程区间还包含渲染与调度，
并非只计 `doThread` 函数实际执行的指令。

全程主线程 CPU 配对变化为 −1.0753%，探索性的单侧上界 +0.3180%；同步返回后的主线程
变化为 −0.8102%，上界 +0.8411%。这些结果说明主线程未见相同量级的净回退，不能据此把
已经失败的进程用户态指标改判通过。

“其他线程”不能直接写成“GL CPU”。进程至少还有原生 `save` 线程、粒子线程和 llvmpipe
渲染线程。源码 `src/serial.c:241` 创建名为 `save` 的线程，`src/particles.c:1217` 创建
名为 `particles` 的线程；已检查日志中的样本启动了 15 条粒子线程。`src/main.c:652–659`
在绘制入口投递粒子关键帧，因此保存期间画面与关键帧调度可能改变后台工作量。
当前 probe 没记录各线程 TID、CPU、绘制次数或关键帧总数，不能区分保存 worker、粒子和 GL。
它也没在完整结束点记录 RUSAGE_THREAD 的 user/system 分量，因此无法精确还原非主线程的
用户态 CPU。上述差額仅为各线程 user+system 合计的守恒分解。

OpenGL 和粒子工作可能跨过计时窗口边界：开始前提交的任务可能在保存区间内完成，保存期间
提交的任务也可能在 `doThread` 返回后继续运行。这是可检验的机制假设，当前没有队列排空
或逐线程证据来确认其量级。不能根据这个可能性直接扣除非主线程 CPU。

AB 顺序的进程 user 平均差为 +25.1771 ms，BA 为 +8.2245 ms；两组分别有 11/15、10/15
对为正。两组都有数值增长，不能只用一个方向的执行次序来解释所有结果。各组逐对差值标准差
约 55.56/52.53 ms，组间均值差不足以独自证明顺序效应。按连续十对查看，平均差依次为
+17.1152、+40.8740、−7.8869 ms；最后十对表现较好只说明存在时序变化，不能摘出来作为
新的通过结果。主机 load average 也不能代替这段进程的 CPU 归因，或成为事后排除样本的依据。

配对 Δ进程 user 与 Δ其他线程 CPU 的相关系数约 0.905，但这两个量共享同一进程 user
测量项，相关性部分来自代数恒等式，不是 GL 或压缩造成回退的因果证据。
Δ完整 wall 与 Δ主线程 CPU 的相关系数约 0.941，也仅用于寻找下一轮测量位置。

主档仍有稳定的体积收益：平均 2,480,461.27 → 2,463,161.13 bytes，约 **−0.69746%**。
其中解压正文固定减少 39,152 bytes，压缩正文平均减少 7,940.13 bytes，ZIP 名称在本地头和
中央目录中的开销另减少 9,360 bytes。体积减少不能补偿未证明的 CPU 条件。

为隔离正文变化对压缩的影响，另行预声明并执行了一个独立离线实验：固定同一份
`baseline-01/game.teag` 的 2,864 个对象正文，只改变真实 `loadObject`/`setLoaded` 的名字
及相应 ZIP 条目名；词法处理保护字符串和序列化字节码，反向变换逐字节恢复原正文。
数据读取、转换、验证在计时之外。使用系统 Python zlib，参数为 level 4、raw DEFLATE、
windowBits −15、memLevel 8、默认 strategy；固定 2 轮预热及 **24 对 AB/BA**，全部保留。
协议在计时前写入 [failure-analysis-compress-protocol.json](failure-analysis-compress-protocol.json)，
结果与源码分别见 [failure-analysis-compress-results.json](failure-analysis-compress-results.json)
和 [failure-analysis-compress.py](failure-analysis-compress.py)。

局部用户 CPU 配对变化为 **+0.3662%**，描述性的双侧 95% 区间 **[+0.1398%, +0.5931%]**。
更短文本并不保证更少压缩 CPU；但这次局部增加约 0.22 ms，没有复现十几毫秒的增加量级。
这个实验没有运行游戏自带 zlib 的 worker，没有 Lua 命名、CRC、ZIP 元数据写入、I/O、
并发争用、粒子或渲染；Python 调用与分配开销也仍计在其中。因此不能把 0.22 ms 当成游戏
worker 的精确增量，不能从正式结果直接扣去它，也不能用它证明完整保存的 CPU 条件。

当前正式对照比较了两个完整包：除 Base62 外还包含库存和 Fearscape 模块的安装。
普通保存场景没有加入新库存物品；这批数据无法估计未来库存事件规范化后减少对象正文的收益，
也不能把整包差异全部归给 Base62。两个新模块会改变加载阶段的分配和稍后的 GC 状态，
这也是下一轮默认组合需要独立测量的理由。

主代理已把 Base62 默认关闭，并使字母表只在明确启用时分配，默认继续使用 0.2.10 的十进制
命名路径。已另行预声明两个各 30 对的新数据集：普通原档保存，以及经真实 table-id
`addObject` 加入 24 件标准 gem 后的保存；双方都独立对照原 0.2.10。新样本不与本批合并。
普通场景可检验默认模块安装是否带来额外成本；新物品场景可检验库存规范化的实际体积收益和
完整 CPU 条件。两者都应保留原 RUSAGE_SELF 用户态主指标和同一 1% 单侧上界门槛。

若将来继续定位 opt-in Base62，可先声明一个小型机制诊断批次：在同一新包内切换十进制与
Base62，以隔离命名选择；同时保留原 0.2.10 作为安装成本控制。预先均衡三种顺序，记录
`save`、`particles`、llvmpipe 线程的 CPU、区间内绘制次数和关键帧数，以及同步结束、
worker 开始、完整结束三个边界。`/proc/<pid>/task` 可按名字识别线程，`schedstat` 可读
线程运行时间；它不能单独给出用户态分量，`stat` 的 user/system 又有计时刻度限制。
新诊断必须说明这种精度与读取扰动，不应假装已经取得现有数据没有的 GL 精确值。

这个方案可以分别证伪几个假设：若仅切换 Base62 增加保存线程 CPU，继续检查名称文本压缩；
若保存线程不变而粒子/渲染工作随关键帧数变化，继续检查区间边界与调度；若十进制的新包
对原包仍回退，检查模块安装和 GC 状态。只优化 Base62 的除法或拼接不能由当前 +16.7 ms
结果自动得到支持；它至多是另一个需要独立验证的微小候选。
